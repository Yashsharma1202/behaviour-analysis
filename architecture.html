Behaviour Analysis · d:\behaviour analysis · as of 14 Jul 2026

How Indian stocks move around corporate events

A self-contained research stack that pulls NSE corporate-event feeds and price history, asks how many days before an event you should buy and how many days after you should sell, and then — this is the part that matters — tries hard to prove its own answer wrong. Pure Python standard library plus pandas. No web framework, no charting library, no cloud.

1What this project is

One research question, three layers of machinery built to answer it.

Indian listed companies broadcast four kinds of scheduled corporate event to the NSE: quarterly results, board meetings, corporate actions (dividends, splits, bonuses) and announcements (press releases, acquisitions, order wins). Each has a known or knowable date. The question this project exists to answer:

If an event is coming on day T, is there a T−N entry and a T+M exit that reliably makes money?

Everything else — the downloaders, the two web dashboards, the XBRL-to-Excel converter, the price cache — is scaffolding around that one question. The final section of this document is the answer, and it is not the answer the dashboard originally gave.

2Architecture

Four layers, strictly one-directional. Nothing downstream ever writes back upstream, so any stage can be re-run from scratch without corrupting the one before it.

Layer 1
Ingestion

Pull from two external sources, survive their defences

NSE sits behind an Akamai bot wall that returns 403 unless you carry a primed cookie jar. A single long-lived session is kept alive process-wide, re-primed only on failure, with exponential backoff (0s → 2s → 5s) and per-feed isolation so one dead feed doesn't kill the other three. Prices come from the Yahoo chart API and are cached to disk on first fetch.

stock_server.fetch_nse_feeds() download_feeds.py event_behaviour.fetch_prices_yahoo()
Layer 2
Storage

Flat CSV on disk — the whole database

There is no database. Fundamentals live in five statement folders keyed by symbol; event feeds live in one folder per symbol; every derived artefact lands in processed/. This makes every intermediate result inspectable in Excel, which is the entire point.

balance_sheet/ pnl/ cash_flow/ quarterly/ ratios/ <SYMBOL>/*.csv processed/price_cache/
Layer 3
Analytics

Event study, then adversarial validation

The behaviour engine grids every entry T−1…T−8 against every exit T+1…T+8 and scores all 64 cells per event type. The backtest engine then takes that same machinery and attacks it: train/test split, market adjustment against the Nifty, and month-clustered t-statistics to stop overlapping trades from faking significance.

event_behaviour.py nifty_backtest.py results_tracker.py next_result.py
Layer 4
Presentation

Three surfaces, one engine

stock_server.py holds all the logic and serves the full 2,363-stock dashboard. nifty_dash.py imports it, swaps the symbol universe for the Nifty 50, and binds a different port — the two never share state. build_static.py bakes a JSON snapshot for GitHub Pages, which cannot run Python.

:8000 / :8080 — full :8090 — Nifty 50 docs/ — static Pages

3The workflow, end to end

This is a sequence — each stage consumes the previous stage's file on disk, so you can stop, inspect, and restart anywhere.

1

Download event feeds

Four NSE JSON endpoints per symbol. Resumable — a symbol is considered done once its financial_results.csv exists, so a rate-limited run just gets re-run. Two-second pause between symbols.

in NSE corporate APIs → out <SYMBOL>/announcements.csv, board_meetings.csv, corporate_actions.csv, financial_results.csv
2

Normalise events into one table

Each feed has its own date column — broadCastDate, bm_date, exDate, sort_date — and its own idea of what a row means. These collapse to a single (symbol, event_date, event_type) spine. Announcements are filtered to major categories only; the rest is noise.

in raw feed CSVs → out unified event table (in memory / processed/unified_events.csv)
3

Fetch and cache prices

Adjusted daily closes from the Yahoo chart API, written once to processed/price_cache/ and never re-fetched. Adjusted, so dividends and splits don't masquerade as returns.

in Yahoo chart API → out processed/price_cache/<SYMBOL>.csv
4

Grid every entry against every exit

For each event, walk back 1–8 trading days for the entry and forward 1–8 for the exit. 64 candidate rules per event, scored on return %, return ₹, and win/loss. Cells with fewer than 10 events are discarded.

out processed/event_behaviour_detail.csv, event_behaviour_summary.csv
5

Serve it — and this is where it gets dangerous

The dashboard reads the summary and prints the winning cell per event type as a card: "buy 7 days before, sell 5 days after, 68% win rate." Everything up to here is honest arithmetic. But the number on that card was fitted on the same data it is being reported on. It is a description of the past, not a prediction.

out /api/behaviour → Behaviour tab
6

Attack the result

Fit the rule on the oldest 70% of events. Apply it, untouched, to the newest 30%. Subtract the Nifty. Charge 0.10% round-trip cost. Cluster the t-statistic by calendar month, because 49 stocks trading the same days are not 5,382 independent bets.

out processed/nifty_backtest.csv → see §8

Reading the grid

Each square is one rule. The starred cell is the winner the dashboard reports for RESULTS events: buy 7 trading days before, sell 5 days after.

Each cell is scored on average return %, average return ₹ and win rate, across every event of that type. Cells backed by fewer than MIN_EVENTS=10 events are thrown away — with too few samples, the "best" cell is just the luckiest one.

Selection is win-rate first, then average return. That is a deliberate choice: a rule that wins 68% of the time and makes a little is more believable than one that wins 40% of the time and got saved by two enormous outliers.

The trap built into this design

Picking the best of 64 cells on the same data you then report is selection on noise. With 64 tries, something will look good even if nothing is. That is exactly what §8 sets out to measure — and it found what it was looking for.

8Validation — the honest result

Fit on the oldest 70% of events. Apply, untouched, to the newest 30%. Subtract the Nifty. Charge 0.10% cost. Cluster the t-statistic by month. Then look.

Two things collapsed under scrutiny

The t-statistic was inflated 13× by pretending trades were independent. Forty-nine stocks trading the same calendar days are not 5,382 independent bets — they are a few hundred correlated market days. Averaging trades within each month first, then testing, dropped the RESULTS t-statistic from +3.03 to +0.23.

The edge did not survive leaving the training window. Market-adjusted RESULTS went from an in-sample t = +2.44 to an out-of-sample t = +0.23. The raw out-of-sample number still looks handsome (+1.64%) — but only because the test window happened to be a bull market. That is the market's return, not the event's.

And one flaw I found in my own control

32 of 48 stocks showing a positive market-adjusted edge looks encouraging — better than a coin flip. It probably isn't. Look at who tops the list: BEL +3.07%, APOLLOHOSP +1.97%, ADANIENT +1.74%, ADANIPORTS +1.58% — precisely the stocks that massively outran the Nifty over the test window. Subtracting the index's return does not remove the stock's own drift. For a stock that tripled, any long position over any twelve-day window shows a positive "market-adjusted" return, and the event has nothing to do with it.

The mirror image confirms it: the bottom of the table is HINDUNILVR −1.30%, BRITANNIA −1.18%, ASIANPAINT −0.89% — the FMCG names that underperformed over the same period. This is measuring stock selection, not event behaviour.

The decisive test is still outstanding: compare each event window against the same stock's return over random windows of the same length. That removes the stock's own drift and leaves only the event effect. My expectation is that the edge shrinks to roughly zero.

Where this leaves the dashboard. The Behaviour tab's cards are arithmetically correct and analytically misleading. They describe what already happened; they do not forecast. The tab needs a banner carrying these out-of-sample numbers alongside the in-sample ones.

Random-window placebo control. Compare event windows against the same stock's own random windows, not against the Nifty. Decides whether any event edge exists at all. Everything in §8 is provisional until this runs. blocking
